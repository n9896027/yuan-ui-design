# Interaction Truth Contract

在实现或审计按钮、表单、拖放、异步操作、持久状态、重试、撤销、回放或跨页面主链时读取本文件。

## 核心规则

界面中的主要动作必须连接产品状态，而不是只改变装饰。为每个主交互记录：

| 字段 | 要回答的问题 |
|---|---|
| Intent | 用户为什么做这个动作？ |
| Preconditions | 什么状态下允许操作？ |
| Trigger | 点击、键盘、触控、拖拽或系统事件是什么？ |
| Transition | 从哪个状态到哪个状态？ |
| Observable consequence | 用户立即看到或听到什么变化？ |
| Source of truth | 变化来自本地草稿、客户端状态、服务器还是外部系统？ |
| Persistence | 刷新、返回、重开或跨设备后是否保留？ |
| Failure | 超时、拒绝、冲突或断网时发生什么？ |
| Recovery | 用户如何重试、撤销、修正或继续？ |
| Evidence | 用 DOM、状态、请求、数据库替身、trace 或 Replay 证明什么？ |

不是每个产品都需要服务器、持久化或撤销。只有适用字段才实施；不适用时明确写出，不能让界面暗示并不存在的能力。

## 已观察事实与提议

先从代码、协议或真实运行中确认 source of truth。没有这些输入时：

- 用“现有转派命令”“提议的本地草稿存储”等语义占位，不发明具体 API 路径、数据库表、字段或服务端保证；
- 把状态机、幂等、撤销、冲突或持久化要求标为 proposed，直到现有实现或产品决定确认；
- 只有实际观察到请求、响应和刷新结果后，才把“会保存”“可重试”“跨设备同步”等写成现状；
- 规格可以提出需要的契约，但不能把提议写成已经存在的事实。

## 真交互硬门

主交互只有在以下四项同时存在时才算通过：

1. 用户能辨认操作入口；
2. 操作触发真实状态迁移；
3. 迁移产生可感知后果；
4. 测试能断言该后果，而不只看到动画。

以下都不能单独作为真交互证据：

- hover、按压、发光、粒子或音效；
- 镜头平移、旋转或缩放；
- 前端临时改字但刷新即丢失，而页面声称已保存；
- 点击后永远成功的假 toast；
- 录屏中“看起来动了”但无状态或网络断言；
- 选择题包在 3D 场景中，但场景操作不影响解题。

## 预览、提交与确认

- **Preview/draft**：允许自由试验，明确尚未提交；预览不得冒充正式结果。
- **Pending**：操作已发出但结果未知；显示进度，避免重复触发造成歧义。
- **Committed**：只有真实 source of truth 确认后才显示已保存、已发送或已完成。
- **Failed**：保留仍有价值的输入，说明什么没发生，并提供适当恢复路径。
- **Stale/conflict**：发现版本冲突时不得静默覆盖；告诉用户正在比较、刷新或重新应用。

若使用 optimistic UI，记录临时状态、确认条件和回滚行为。不要为“更快”而隐藏失败。

## 重试与重复操作

- 明确操作是否安全重试、需要幂等保障、只能查询状态，或必须让用户重新确认；具体机制服从现有系统契约。
- 网络结果不确定时，不要自动制造第二次副作用。
- 防重复点击不能只靠视觉禁用；必要时让状态层或服务端也拒绝重复提交。
- 重玩或重做若代表新记录，应创建新身份；历史结果保持只读。不要把覆盖旧结果伪装成 Replay。

这些要求只在任务确实包含外部写入或不可逆状态时使用，不能把普通本地筛选器复杂化成分布式事务。

## 既有值、草稿与异步回执

有“编辑旧数据”的主链，至少区分四个值：已读出的 committed 值、当前对象 ID、尚未提交的 draft、以及某次请求发出时的 snapshot。它们相同的时候很常见，但不能因此混用。

| 情况 | 真实后果 | 不能声称 |
|---|---|---|
| 初载尚未完成 | 等待或显示读取状态；不写回默认内容 | “空白就是没有旧值” |
| 已保存空文本 | 读回仍为 `""` | “恢复默认文案” |
| 切换到另一段 | 当前段的草稿按 ID 留在会话中 | “另一段已保存” |
| 编辑后回执迟到 | 确认旧 snapshot，当前新草稿仍为 dirty | “输入框里的新值已保存” |
| 未编辑点击保存 | no-op 或现有契约定义的安全提交 | “为了保险重置字段” |

对异步提交建立一个可观察的版本界限：提交时记录 `{ id, revision, snapshot }`；回执回来后，先落入该 `id` 的 confirmed 状态，再检查当前选择和 revision 是否仍相同。只有仍相同，才可将 UI 置为 committed。读取时同样以字段存在性而非 truthiness 判断：空字符串和空草稿是数据，不是缺失。

最低证据应包括：旧值初载、已保存的空文本、空草稿切换回来、未编辑保存、多段切换、编辑期间的迟到回执、重新读盘、以及键盘路径。每项同时断言可见状态和对应存储/请求记录。练习中的 [字幕回归实现](../evals/subtitle-persistence/README.md)故意保留一个会失败的旧版本，作为“绿灯不等于保护了当前草稿”的反例；它不是通用生产测试或远端一致性证明。

## 输入路径

为关键动作选择与语义匹配的输入：

- 点击/触控：命中区明确，不能依赖 hover 才发现功能。
- 键盘：焦点顺序可预测，Enter/Space/方向键遵循控件语义。
- 拖拽：同时提供选择后放置、移动按钮、菜单或其他单指非拖拽路径。
- 手势：提供可见控件或等价操作，不把捏合、摇晃作为唯一入口。
- 语音/屏读：状态变化要有合适名称和通知，避免每个视觉变化都打断用户。

替代路径必须改变同一个 source of truth，不要维护一套“无障碍假流程”。

## 让同一状态用于设计审阅和交互验证

借鉴 Storybook 的命名示例。给最容易画错或做错的几个状态一个稳定入口，并用现有表单、组件或路由呈现它们。项目已有 Storybook 时，可用 args 提供内容、用 play 操作界面。单文件或原生工程可以用查询参数、预览参数或已有测试夹具实现。[命名示例](https://storybook.js.org/docs/writing-stories) · [交互测试](https://storybook.js.org/docs/writing-tests/interaction-testing)

| 工单状态 | 如何到达 | 看什么、做什么 |
| --- | --- | --- |
| 长设备名 | 将真实长度的名称放入 W-02，打开正常编辑表单 | 在手机查看队列中的名称，再定位本次编辑对象与保存按钮。 |
| 保存中 | 修改备注并提交，让受控的保存回执暂时停住 | 截图时状态保持稳定。尝试重复提交，再放行回执，检查写入值与当前草稿。 |
| 失败后保留草稿 | 触发下一次保存失败，再提交同一份输入 | 同时核对旧存储及新草稿，键盘重试，然后刷新读取实际保存值。 |
| 已保存并重开 | 通过正常提交流程保存记录，真正刷新页面 | 检查输入框、列表摘要与持久化记录仍一致。 |

快照和自动化共用同一个命名入口。对场景使用隔离的演示数据，保留用户普通入口的本地记录。特别注意重载时的初始化：一旦已有保存回执，再进入同一状态应能读出刚刚保存的值。截图记录同时注明屏幕尺寸、场景名和被查看的工单。

## 验收方法

对每个关键交互至少验证：

1. 建立可复现前置状态；
2. 用一种真实输入触发；
3. 等待实际状态、响应或事件，不用固定延时猜测；
4. 断言可见结果和底层 source of truth；
5. 若声称持久化，刷新或重新进入后再断言；
6. 存在失败条件时，触发一个真实失败并验证恢复；纯本地筛选等无此边界的动作不制造失败；
7. 用第二种必要输入路径验证同一迁移。

记录精确操作、状态前后值、请求或 trace、结果和证据环境。无法触发的失败路径标为未验证，不用 Mock 冒充生产失败。

# Yuan-UI-design v2.5.0-dev.4

Yuan-UI-design 学习可公开复用的产品设计方法，视觉方向来自当前产品的任务、内容与设计系统。目标不是“做得像某个 AI 产品”，而是把真实产品任务变成有辨识度、可操作、可验证的界面。

## 结果标准

完成的界面必须同时满足：

- **有用**：用户能看懂当前任务，并完成它。
- **真实**：可见控件连接真实状态；预览、提交、失败和持久化边界清楚。
- **独特**：视觉语法来自产品内容，不套默认 AI SaaS 外壳。
- **包容**：键盘、触控、指针和辅助技术有与任务匹配的路径。
- **克制**：动效、3D、AI 助手和装饰只在帮助理解或操作时出现。
- **可证**：只声明实际运行并观察到的结果，明确证据环境和限制。

## 按需读取

不要一次加载所有参考。遇到相应任务时完整读取：

- 目标宿主影响导航、输入、系统能力、生命周期或验收时，读 [references/platform-surfaces.md](references/platform-surfaces.md)。同为网页，阅读型网站与长时间编辑的 Web App 可有不同结构。普通文案或配色修正可直接沿用当前平台。
- 有按钮、表单、异步提交、持久状态、重试或主任务流：读 [交互与命名状态](references/interaction-truth.md)。需要同时重看画面和验证操作时，为同一份实际表单提供可复现的状态入口。

- 从截图或竞品提炼风格，或设计后台、落地页、编辑器的视觉系统时，读 [references/visual-quality.md](references/visual-quality.md)。
- 用户要求 Unslop、去 AI 味或修整已有屏幕的模板感时，读 [Unslop 视觉精修](references/unslop.md)。若只给网址，先对照同尺寸原屏和离线副本，确认能复现后再改稿。
- 用户需要凭图辨认实物、挑选照片，或为多张插画保持一致的美术方向时，读 [配图与选图](references/image-direction.md)。先明确读者要凭图找到、辨认或比较什么，在目标视口试做这个动作，再安排解释、揭晓或提交。

- 有 AI 生成、工具执行、长任务、用户接管或中断恢复：读 [references/agentic-ui.md](references/agentic-ui.md)。普通页面不加载。

## 权限与边界

- 先服从用户的产品目标、技术栈、品牌和范围，不用本 skill 偷换需求。
- 优先沿用 repo-native 组件、tokens、路由、状态和测试设施；除非收益明确，不引入重依赖。
- UI 实施授权不自动授权 API、数据库、生产部署、付费生成或外部发布。
- 依现有请求和会话授权判断可执行范围；不要为已授权的例行步骤重复索要确认。提议外部动作前先完成授权范围内可供审阅的工作。
- 不读取凭据、私密数据或生产数据库来填充界面。
- 可以提炼参考的结构、比例、密度、节奏和交互模式；不得复制品牌身份、专有代码、文案、素材或像素级商业外观。
- 若用户只要一张视觉图，使用图像生成流程；不要假装已实现网页。

## 七个硬门

### 1. 产品任务门

在写样式前，用一句话说明：**谁在什么情境下，要完成什么任务，完成后看到什么变化。** 无法回答时，先从现有代码、内容和用户请求中补足，不凭空发明产品。

### 2. 信息层级门

先区分：

- 当前核心任务；
- 完成任务必须看到的对象或状态；
- 辅助信息、历史、解释和帮助。

壳层由任务决定。不要默认左侧导航、卡片网格、右侧 AI 助手或暗色控制台。

### 3. 交互真实性门

每个主交互都要有：

```text
用户动作 -> 状态变化 -> 可见后果 -> 可验证证据
```

查看类任务可以用可观察的结果验收，例如用户从预设视角认出被遮挡的部件。配置、编辑和提交还要核对对象状态的实际变化。

### 4. 状态完整门

只实现任务实际需要的状态，但不要遗漏关键边界：default、focus、active、loading、empty、success、error/recovery、disabled/locked，以及适用时的 offline、stale、partial、replay。预览态与已提交态必须可辨；失败不能伪装成功。

改已有编辑器时，用一条预先存有内容的记录从正常入口打开，原样保存、重开并逐字段对照；再实际将一个允许清空的字段清空，验证它仍可保存为空。若存在异步回执，检验迟到的结果是否覆盖另一对象或更新的输入。

### 5. 输入等价门

按宿主实际支持的输入提供可达路径。Web 和桌面空间控件支持键盘及可见焦点，触屏拖拽提供点选等替代。减少动态效果时保留必要反馈。渲染不可用时用目标视图、列表或数值控件承接可表达的任务，说明仍需三维设备或能力才能完成的部分。

### 6. 反模板门

拒绝下列默认答案：

- 一屏漂浮卡片、渐变、毛玻璃和发光边框；
- 与产品无关的“AI 驾驶舱”、聊天侧栏或粒子背景；
- lorem ipsum、空泛指标、虚构能力和无意义图表；
- 把桌面布局压窄后称为移动端；
- 用 3D 当壁纸，再把真实任务退化成选择题。

### 7. 证据诚实门

所有验收结论标明证据级别：

- `static`：代码、设计稿或静态截图；
- `mock`：Mock 数据或替身服务上的运行结果；
- `local-runtime`：本地真实应用链；
- `staging`：可部署候选环境；
- `production`：线上实际环境。

截图只能证明画面；DOM 只能证明当前结构；Mock 不能证明真实 API；实验室性能不能冒充真实用户数据。不得把证据升级到高于实际环境的级别。

## 工作方式

### 按任务选择深度

- **草图/规格**：仅交付文字、设计稿或验收计划时统一标 `static`。只有实际运行使用替身的界面并观察到结果，才将相应结果标 `mock`。
- **功能/局部修复**：沿用现有系统，完成受影响主链与必要失败恢复；验证改动影响，不重做无关页面或强制多方案探索。
- **正式交付/质量声明**：覆盖请求范围内的状态、输入和环境；正式验收再生成可机读证据并运行严格校验。

根据用户目标和实际风险选深度，不能用“原型”降低用户要求，也不能把轻量改动扩成全站审计。

### 理解现状

- 找出真实入口、设计系统、组件库、内容、数据来源、路由、状态管理和现有测试。
- 检查工作树，保护用户已有改动；不要为了统一风格重写无关页面。
- 识别最重要的主链和一个高风险失败链。
- 将仓库中已观察到的事实与提议方案分开。未检查到真实 API、存储或状态语义时，不发明具体端点、字段、表名或持久化保证。

### 定义设计语法

高视觉新建或大改版先按 `visual-quality.md` 比较轻量方向；只交规格时也简述方向差异与选择理由，不直接省略为单一风格。明确品牌、设计稿和局部修复直接沿用。素材、组件和内容应共同解释产品，而不是各自追求装饰效果。

先确定一句话视觉概念，并说明它为什么服务产品。再定义或扩展：

- semantic color、typography、spacing、shape、depth、motion tokens；
- 组件语义、密度和状态，而不是孤立样式；
- 真实内容长度、语言和数据形态；
- 响应式重排规则，不只是断点数字。

已有 tokens 时优先扩展。需要跨工具交换时，可采用带 `$type` 和 `$value` 的 DTCG token 格式；不要为了格式迁移破坏现有构建。

### 先做完整纵切

含主任务交互时，优先完成可操作纵切：真实内容、主要动作、结果、适用的失败恢复和目标设备都能走通。纯内容/样式任务先完成一份有代表性的页面或改动范围，不制造主动作或失败状态。通过后再扩展装饰、更多卡片、动画或 3D 场景；验证深度遵循下文按能力分级。

### 实现后批评

至少检查：

- 三秒内能否理解页面和下一步；
- 视觉焦点是否与任务优先级一致；
- 若有主控件，是否真的改变状态并产生后果；
- 是否出现任何无作用、假装保存或假装联网的元素；
- 中文、英文和长内容是否改变布局；
- 产品支持的设备、所需输入和实际存在的失败状态下，是否仍可完成任务；
- 视觉是否带有产品自己的识别线索，而不是 AI 模板味。

发现问题就迭代，不以“一次生成”作为完成标准。

## 验证最低要求

按改动涉及的能力选择验证，不能用正式交付之名制造无关测试：

- **仅草图/规格**：标 `static`。把真机、模拟器、浏览器或替身上的后续检查写为“待执行”，包括打算使用的输入、失败情境和通过条件。
- **纯内容/样式实施**：检查受影响页面的排版、长内容和适用视口；若影响交互元素，再检查键盘/触控与状态。没有异步操作时不制造失败、网络或提交断言。
- **含状态、异步或外部写入**：真实操作受影响主链及一个适用的失败/恢复路径，检查所需输入；用目标宿主的 UI/可访问性树、状态或请求断言证明后果，声称持久化时重进验证。
- **响应式/无障碍/性能改动或声明**：检查对应环境与能力。面向桌面和移动的布局实施至少检查两类代表视口；触控、拖拽替代、Reduced Motion、forced colors、无 WebGL 等按受影响能力选择。

运行检查时记录环境、构建身份、命令、关键截图/trace、通过/失败/未测项，并检查对应的运行错误、请求失败、布局溢出和文本截断。浏览器、模拟器与真机各自记录。无法运行就明确未验证，不凭空补通过项。

正式声称 WCAG、屏读、真实 200% zoom、Core Web Vitals 或生产可用前，必须使用对应真实工具和环境。自动化扫描或模拟视口不能独自证明这些结论。

## 交付格式

先给结果，再给必要证据：

1. 一句话设计方向与产品理由；
2. 已完成的用户任务和真实交互后果；
3. 主要改动文件；
4. 验证矩阵与证据级别；
5. 未验证或受环境限制的项目。

只写规格时，至少包含目标、当前问题、设计方向、信息架构、tokens、组件语法、状态/交互契约、响应式、无障碍、性能、文件级改造和验收边界。不要默认创建报告文件，除非用户需要。

## 可机读证据

需要正式验收时，可按 [references/verification.md](references/verification.md) 记录 JSON，并在本技能目录运行：

```bash
node scripts/validate-ui-evidence.mjs --strict --check-local-evidence <evidence.json>
```

交付摘要分别说明记录结构及所检查的证据路径是否有效、严格验收是否通过，并点出影响用户的失败项。以上命令启用严格类别/声明能力覆盖和本地路径存在性检查；它不判定行为是否真实发生，也不鉴定文件归属或内容。独立复核实际产物仍是验收的一部分。严格模式会拒绝所有远程 `http(s)` evidence 或 assertion URI。只有确有必要时，才可显式运行：

```bash
node scripts/validate-ui-evidence.mjs --strict --check-local-evidence --allow-remote-evidence <evidence.json>
```

放行不是静默例外：报告必须为每个远程 URI 在 `remoteEvidence` 中提供且只提供一条 `{ uri, reason, reviewMethod }` 记录；证据和 assertion 的 URI 都必须一一匹配，无多余、缺失或重复。`limitations` 可以说明剩余边界，但不能替代该记录。这个脚本不会抓取远程内容；`reviewMethod` 必须让验收者能独立复核。它也不代替浏览器、Axe、真实屏读、真实 zoom 或现场性能测试。
